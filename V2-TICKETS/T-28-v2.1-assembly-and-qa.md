## Context

Every V2.1 piece exists. This ticket wires them into `VisitWorkspace`, then walks the five scenarios
checking that the columns tell the same story — the same discipline `T-18` applied to V2, against a
harder target, because the state is now four independent facets instead of one enum.

Four consistency contracts are load-bearing:

1. **`aiError` ⇒ nothing was written by the failed call.** Log ends in a red `504`, error copy says
   `Nothing was written to Photon.`
2. **`apiError` ⇒ only the lookup broke.** Instructions still render, patient milestone still green,
   selected-treatment card red, medication prep still visible, handoff `Blocked`, readiness counts
   `Treatment selected` as incomplete.
3. **Dirty patient ⇒ Photon is behind.** Amber badge, `Local edits not yet written to Photon`, and
   the milestone id still showing the *old* synced state.
4. **Stale instructions ⇒ handoff blocked.** Stale banner, and finalize toasts
   `Regenerate instructions for the new treatment`.

## 3. Full walkthrough

From `Fresh visit`, without touching the switcher again:

1. Readiness `0 of 4`. No results, no selection, empty instructions, 1 log row.
2. `Finalize handoff` → toast `Select a treatment first`.
3. Click `hydrocortisone` chip → 3 results, log row `→ 3 results`.
4. `Select` on `Hydrocortisone cream 2.5%` → row tints, button reads `Selected`, medication prep
   appears, `dose` ticks, readiness `1 of 4`, toast names the drug.
5. `Finalize` → `Sync the patient to Photon first`.
6. `Edit patient`, change phone, `Save patient` → toast `Patient saved · run Sync Photon to write
   it`, badge amber `Not synced`… — **verify:** with `patientSync: "none"`, `dirty` does not tint
   the badge (the override only applies to synced/updated), so it stays neutral `Not synced`.
7. `Sync Photon` → `Syncing…` 900ms → badge green `Synced to Photon`, id chip fills, milestones 2/4/5
   green, `allergy` + `interaction` tick, 4 new log rows starting `201`, readiness `2 of 4`.
8. `Finalize` → `Generate the Spanish instructions first`.
9. `Generate instructions` → 1300ms → content, badge `needs review`, readiness `3 of 4`, log row
   `POST /instructions → generated`.
10. `Finalize` → `Mark the AI output reviewed first`.
11. `Mark reviewed` → review card green, instructions badge green, readiness `4 of 4`.
12. `Finalize` → `Complete the safety review first` (lactation still unticked).
13. Tick `lactation` → safety badge green `3 synced · 1 clinician-reviewed`.
14. `Finalize` → green button, green header pill, manifest with the live ids and
      `2.5% · 30 g tube · 7 days · 0 refills`, log row `Handoff prepared · no Rx written`.
15. Select `Hydrocortisone cream 1%` → stale banner, `finalized` clears, handoff leaves `Ready`.
16. `Finalize` → `Regenerate instructions for the new treatment`.
17. `Regenerate instructions` → banner clears, title now reads `…1% — cómo usarla`, manifest
      strength becomes `1%`.
18. `Ejemplo: lactancia` → `Translate` in the action bar → patient bubble with flag pill, toast, one
      `POST /translate → clinical question flagged` row.
19. `Reset demo` → back to `Populated`.

Every step: no console error, no layout jump.

## 6. The live-integration seam

V2.1 ships on fixtures. Wiring it to real Photon and OpenAI is **`T-20`'s** work — its route
designs, Zod validation, `externalId` strategy, and idempotency requirements are still correct.
`T-20`'s *UI* sections are superseded by `T-23`/`T-24`/`T-25` (`T-21 §11`).

Four seams, each with one call site by construction:

| # | Fixture | Call site | Replace with |
|---|---|---|---|
| 1 | `CATALOG.filter(...)` in `runSearch` / `pickQuickTerm` | `T-24 §6` | `GET /api/photon/treatments?term=` |
| 2 | 900ms timer in `syncPhoton` | `T-23 §6` | `POST /api/photon/sync` with the live patient |
| 3 | 1300ms timer + templated `esParas` | `T-27 §1–2` | `POST /api/instructions` with note + patient + treatment |
| 4 | `esToEn` / `enToEs` / `isClinical` | already live via `/api/translate` (`T-19`) | — |

Two known limitations that seam 3 **fixes**, and that should not be patched before then:

- The `esTitle` regex leaves `cream` in the hydrocortisone title (`T-27 §2`). A generated
  `headingEs` has no regex.
- Paragraph 2 hardcodes `dos veces al día, por 7 días` regardless of the note or the `duration`
  field (`T-25`, `T-27 §2`). A real generation reads both.

Patching either in the template hides a stand-in that is about to be deleted. Leave the TODOs.

When seam 2 lands, `syncPhoton`'s three fixture log rows become real ones — and the `201`-vs-`200`
create/update distinction (`T-23 §6`) must come from the actual response, not be inferred from
`patientId !== ""`.
