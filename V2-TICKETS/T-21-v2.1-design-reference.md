# T-21 — V2.1 Design Reference (shared appendix)

**Not a build ticket.** This is the delta between the shipped V2 implementation and the new mockup
`V2-MOCK-HANDOFF/extracted-pt/desktop-mockups-needed/project/Photon Clinic V2.1.dc.html`.

Every ticket `T-22` … `T-28` assumes you have read **`T-00-design-reference.md` first** (the base
design system: type scale, color tokens, badge/button/card recipes, animation) and then this file.
Together they replace the need to open either mockup.

`T-00` is still accurate for everything it describes. This file records only what V2.1 **changes**.

---

## 1. Read this first: V2.1 is a restructure, not an addition

The new mockup does add a patient form and a treatment search. But it also:

- **replaces the `Phase` enum** with four independent state facets (§4),
- **moves** Safety review and Clinician review from the left column to the right,
- **deletes** `PatientContextCard` and the standalone `MedicationPrepCard`,
- **nests** medication prep inside the treatment-search card and makes every field editable,
- **adds** a readiness strip between the header and the body,
- **rewrites** the action bar and the prototype switcher,
- makes the evidence log and sync milestones **live state** instead of phase-keyed fixtures.

You cannot build the patient form or treatment search on the current `phase` model. `T-22` does that
refactor and blocks everything else.

## 4. The state model — read this twice

### V2 (current implementation)

```ts
type Phase = "idle" | "loading" | "review" | "final" | "aiError" | "apiError";
```

One enum conflating *AI status* and *Photon status*. It works only because V2 fired both calls
together and had exactly one patient and one treatment.

### V2.1

Four independent facets, each with its own lifecycle:

```ts
ai:          "idle" | "loading" | "ready" | "error"
patientSync: "none" | "pending" | "synced" | "updated"
txLookup:    "none" | "ok" | "error"
historySync: "none" | "ok"
```

plus new scalar state:

```ts
patient:        PatientRecord        // committed
draftPatient:   PatientRecord        // in-flight form edits
patientEditing: boolean
patientDirty:   boolean              // saved locally, not yet written to Photon
patientId:      string               // "" when never synced

query:      string
results:    CatalogEntry[]
searched:   boolean                  // false = never searched; gates both result states
selectedId: string | null

directions, quantity, duration, refills, pharmNote: string

aiForId:  string | null              // treatment id the current instructions were generated for
clock:    number                     // minutes since midnight, drives log timestamps
log:      LogEntry[]                 // real append-only state
finalized: boolean
```

### Derived

```ts
const sel             = CATALOG.find(c => c.id === selectedId) ?? null;
const isIdle          = ai === "idle";
const isLoading       = ai === "loading";
const isAiError       = ai === "error";
const hasInstructions = ai === "ready";
const isApiError      = txLookup === "error";
const patientSynced   = patientSync === "synced" || patientSync === "updated";
const doseMissing     = !/twice|once|daily|hours|week|day/i.test(note);
const staleForTx      = hasInstructions && sel && aiForId && aiForId !== sel.id;

const syncedCount = ["allergy","interaction","dose"].filter(k => checks[k]).length;  // 0..3
const allChecked  = syncedCount === 3 && checks.lactation;

const canReview   = hasInstructions;
const canFinalize = hasInstructions && reviewed && allChecked
                 && patientSynced && hasSelectionStrict && !staleForTx;
```

### ⚠ `hasSelection` is two different values

The mockup computes it twice with different meanings and uses both:

| name here | expression | used by |
|---|---|---|
| `hasSelectionStrict` | `!!sel && txLookup !== "error"` | readiness strip, `canFinalize` |
| `hasSelectionLoose` | `!!sel` | the `Change` button, medication-prep visibility |

Consequence at `txLookup === "error"` with a treatment selected: the medication prep section and the
`Change` button **stay visible**, but readiness counts the treatment as not selected and finalize
stays blocked. That is coherent — the clinician can keep editing prep while the lookup is broken —
so keep both, under these two distinct names. Do not collapse them.

### Mapping the old enum onto the facets

The V2 → V2.1 correspondence, for reference while refactoring (`T-22`):

| old `phase` | new facets |
|---|---|
| `idle` | `ai:"idle"`, `patientSync:"none"`, `txLookup:"none"`, `historySync:"none"`, no selection |
| `loading` | `ai:"loading"` |
| `review` | `ai:"ready"`, `reviewed:false` |
| `final` | `ai:"ready"`, `reviewed:true`, `finalized:true` |
| `aiError` | `ai:"error"` |
| `apiError` | `ai:"ready"`, `txLookup:"error"` |

Note the last row: `apiError` was always "the AI succeeded but Photon didn't", which the old enum
could only express by special-casing `hasInstructions`. The facets say it directly. The
`hasInstructions` quirk called out in `T-00 §7` and `T-03 §5` **disappears** — do not carry it
forward.

## 6. New shared style recipes

Two form primitives that do not exist in `T-02`. Add them to `app/visit/components/ui/`.

### 6.1 `Input` (new)

```
w-full border border-line-input rounded-[6px] bg-surface-sunken
px-[9px] py-[7px] text-[12.5px] text-ink-2 outline-none
```

Note **`rounded-[6px]`** — inputs are 6px, buttons and textareas are 7px. That is a deliberate
half-step down for the smaller control.

`outline-none` is what the mockup does. Add a focus ring, exactly as `T-06 §1` established for
textareas: `focus:border-brand focus:ring-2 focus:ring-brand/15`.

### 6.2 `FieldLabel` gains a form variant

`T-02 §5` specifies `mb-[3px]`. The V2.1 **form** field labels use `mb-[4px]`, while the
**read-only** cell labels keep `mb-[3px]`. One pixel, but it is the difference between a label
sitting on a 28px input and on a text value.

Add a `dense` prop (default `true` = 3px; `false` = 4px), or accept a `className` override. Do not
change the existing default — every `T-05`…`T-14` call site depends on 3px.

### 6.3 Button sizes gain `xs`

The patient `Edit patient` / `Close` button and the milestones `Sync Photon` button share a size
that is not in `T-02 §4`:

```
px-[11px] py-[5px] rounded-[6px] text-[11.5px] font-semibold
```

Note the **6px radius**, not 7px. Add as `size="xs"` to `Button`. Both call sites use
`variant="ghost"`.

### `DEFAULT_PATIENT`

```ts
{ first: 'Maria', last: 'Gonzalez', dob: '1988-04-12', sex: 'Female', phone: '(718) 555-0142', ext: '' }
```

`phone` is new in V2.1 (V2 had no phone). `ext` (external ID) defaults empty and renders as `none`.

### `NOTE` — changed

V2.1 extends the clinician note with an explicit dose so `doseMissing` is false by default:

```
Suspected eczema flare on forearms. Discussed moisturizing, avoiding fragrance, and short course topical steroid — apply thin layer twice daily for 7 days. Patient asks if treatment is safe while breastfeeding.
```

The added clause is `— apply thin layer twice daily for 7 days` (em dash). This matters: it is what
makes the default demo show full dose instructions, and deleting it from the textarea is how you
demo the dose-omission safety behavior (`T-27 §3`).

## 11. Relationship to the existing `T-20`

`T-20-photon-treatment-search-and-patient-form.md` was written **before** this mockup existed. Its
API-layer work is still correct and complementary:

- `GET /api/photon/treatments` route, Zod validation, live/fixture modes
- `PhotonPatientInput` type, deterministic `externalId`, search-before-create, idempotent re-sync
- route tests

**Its UI sections are superseded** by `T-23`, `T-24`, and `T-25`, which carry the actual design.
Where `T-20` says "add a compact treatment search control" or "add a compact patient form", build
what `T-24` / `T-23` specify instead.

Suggested order: ship `T-22` → `T-23` → `T-24` → `T-25` on fixture data first (fast, demo-visible),
then wire `T-20`'s live routes underneath. `T-28 §6` covers that seam.
